# 商业内容、SEO 与购买阶段统计

## 上线配置

1. 首次接管已有数据库先按 [Prisma 数据库运行手册](prisma-migration.md) 完成基线接管；后续发布运行 `bun run db:migrate`，再构建和重启应用、worker。统计表已包含在 Prisma 基线中，不改已有商品价格和已有订单金额。
2. 在后台「商品与库存」维护商品名称、价格和套餐说明。对比页按套餐内容、适合的用户和本次价格展示；使用建议与官方功能说明分开维护。
3. 在「网站设置 → 服务联系」填写支持邮箱和经过实际验证的 HTTPS 账号信息操作指引地址。指引地址不得包含登录凭据。没有指引时，页面提供联系支持路径，不引导用户自行拼接 Session 字段。
4. 正式环境在**构建与运行时**都设置 `APP_MODE=live` 和正确的 HTTPS `APP_URL`。站点 URL 只能包含 origin，不带路径、查询参数或凭据。演示环境默认 noindex、禁止抓取且输出空 sitemap。
5. 可设置 `GOOGLE_SITE_VERIFICATION` / `BING_SITE_VERIFICATION`，重新构建后完成搜索平台验证，再提交 `/sitemap.xml`。本项目不会自动登录搜索平台或提交站点。

## 页面与索引

- `/compare`：当前在售普通套餐的真实价格、配置说明与全部档位链接。
- `/upgrade`：升级条件与报价说明，链接各升级详情。
- `/help/payment`：查单、到账、更新账号信息、取消与钱包退款。
- 商品详情：独立标题、描述、canonical、分享 metadata、面包屑及 `Service` JSON-LD。确定价格的服务才带 `Offer`；升级和待更新价格不填虚构报价。Service 标记不承诺商品富结果资格。
- `/opengraph-image`：自包含 PNG 分享图片，生成不依赖外部字体服务。
- 正式 robots 允许读取页面 noindex，仅阻止 API 抓取。账户、订单、后台等仍保持 noindex，数据权限仍由原认证与授权逻辑保护。
- 不填虚构评价、成功率、销量、处理时效或修改时间。
- 联系邮箱及账号操作指引由服务端直接渲染；页脚也有服务端提供的联系入口，不依赖爬虫请求 `/api/bootstrap`。同一请求内复用公开配置读取，只输出联系邮箱和指引地址。
- 首页承接充值与套餐价格；`/compare` 承接 Go、Plus 与 Pro 选购；`/upgrade` 承接已有订阅的升级条件和报价；`/guide` 承接账号准备与购买步骤；`/help/payment` 承接未到账、查单和退款问题。每页使用独立标题及明确的 H1。
- 套餐详情按档位提供选购建议，并区分固定充值价格与升级报价，提供可见面包屑及相关指南链接。建议不是功能或额度保证；期限与交付内容由运营维护商品说明，不根据套餐名称自动推断。

## 发布后的 SEO 验收

1. 用正式域名检查首页、对比页、指南和一个在售套餐详情：HTTP 200，title 与 H1 符合页面主题，canonical 为该页正式 HTTPS 地址，正文 HTML 中已有联系邮箱与指引链接。
2. 检查 `/robots.txt` 允许抓取公开页面，`/sitemap.xml` 仅含正式域名的公开页面和在售套餐。账户、订单、结算及后台页面仍输出 noindex；不存在的套餐返回 404。
3. 在 Search Console 与 Bing Webmaster Tools 完成站点验证并提交 sitemap，再用 URL 检查确认正式页面可被抓取。平台验证需要对应域名或账号权限；代码部署不等于完成平台提交或已被收录。
4. 每周按查询词及落地页记录展现、点击、CTR 和平均排名，再结合站内搜索来源的购买阶段计数调整标题与内容。没有搜索数据时不推断搜索量或排名收益。
5. 运营更新实际套餐内容、期限或价格时，同时复核详情和对比说明。未配置联系方式时页面明确提示未公布；不要发布虚构联系方式或承诺。

本地回归：`bun run check`、`bun run test`；独立测试库配置后运行 `bun run test:e2e tests/seo-growth.spec.ts`。该 E2E 使用隔离 schema 中的示例联系方式，验证原始 HTML 中的真实链接、独立 metadata、noindex、404 与移动端对比页。`src/indexing.test.ts` 覆盖演示及正式环境的 robots / sitemap 策略。

## 统计口径

客户端仅可上报 `plan_view`（详情页）、`checkout_view`、`verify_started`，接口严格拒绝额外字段和财务事件，限制请求体与调用频率。浏览阶段按浏览器、商品、UTC 日期去重。

报价成功由服务端写入；订单创建、付款、交付、钱包退款由数据库状态变化写入，订单与阶段组合唯一，重试不重复计数。纯余额订单也记录付款；钱包充值不算套餐成交。旧订单不回填未知的历史阶段。

来源仅为 `direct/google/bing/baidu/referral/other`。每个浏览器标签页会话保存首次来源；只读取 UTM source 及邀请参数进行分类，不保存完整 URL、UTM campaign、搜索词、邀请代码或 referrer。它是来源分类，不是广告或真实搜索曝光的认证。

统计使用与业务浏览器摘要分离的哈希标识，不采集邮箱、账号会话、密码或支付凭据，不接入第三方分析服务。尊重 DNT/GPC：不发送浏览事件、不关联新报价。后台显示最近 30 天各阶段和来源；各阶段是独立活动计数，不是同一批访客的严格漏斗，也不直接计算转化率。直接从首页购买会跳过详情页。

worker 每小时清理超过 90 天的明细及旧报价统计关联。要执行留存策略，必须持续运行 worker。演示和生产应使用独立数据库，避免测试流量进入正式报表。订单数据、会计记录与佣金继续按原业务规则保留。

## 下一步需要真实数据的工作

- 根据 Search Console 展现、点击和查询词调整标题与选题。
- 根据各阶段的真实流失情况决定是否改购买流程。
- 贡献利润需要完整的上游成本、支付手续费与售后成本；当前统计不把成交额标成利润。
- 续费提醒需要可靠的实际到期日和用户意愿，未按购买日期猜测期限。
