# ZEN 统一风控

应用内嵌 `@gorules/zen-engine`，由本地 JDM 决策表管理业务限流、验证码要求、自邀与首单返佣规则，以及订单和提现关联规则。规则不从请求或远程地址加载，不向 GoRules 发送业务数据，无需单独部署规则服务。

## 规则与执行

- `src/server/risk/limits.json`：场景、关联维度、计数窗口、阈值、执行模式和原因码。ZEN 根据场景及 demo/live 模式返回计数策略。
- `src/server/risk/decisions.json`：根据计数与业务事实输出 `allow`、`deny`、`challenge` 或 `review`。第一条命中的规则优先；末尾为默认放行。数据形状由服务端验证，未知场景、无效事实、原生引擎执行错误不会默认放行。
- `src/server/risk-policy.ts`：加载、验证及执行决策表。版本为两个文档内容的 SHA-256 摘要前缀；每次决策记录实际规则版本。
- `src/server/risk.ts`：可信 IP、HMAC 关联标识、数据库原子计数、验证码执行及决策留存。

规则随代码评审、测试和发布。后台“风控记录”只读展示最近 100 条记录，需要 `audit:read` 权限。当前不提供在线改规则、自动封号或自动打款。业务决策记录与业务修改使用同一事务；限流计数在拒绝前提交，不因拒绝回滚。

## 旧规则迁移

| 场景                             | 当前阈值                                                   | 迁移行为                                                                               |
| -------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 浏览事件                         | 浏览器 120 次 / 分钟                                       | 原额度的 2 倍                                                                          |
| 报价                             | 浏览器 12 次 / 分钟；正式模式上游全局 12 次 / 分钟         | 原额度的 2 倍                                                                          |
| 下单                             | 浏览器 24 次 / 10 分钟                                     | 原额度的 2 倍                                                                          |
| 联系邮箱下单                     | 请求含联系邮箱时，每邮箱 10 次 / 10 分钟                   | 原额度的 2 倍                                                                          |
| 上游下单预检                     | 正式模式全局 12 次 / 分钟                                  | 原额度的 2 倍                                                                          |
| 更新 Session                     | 浏览器 12 次 / 分钟                                        | 原额度的 2 倍                                                                          |
| 发送验证码                       | 正式模式每邮箱 3 次 / 10 分钟，全局 1000 次 / 10 分钟      | 继续执行；演示阈值仍为 100 / 10000                                                     |
| 后台刷新汇率、导入库存、提现估算 | 每用户分别 12、20、60 次 / 分钟；提现汇率刷新 12 次 / 分钟 | 原额度的 2 倍                                                                          |
| Turnstile                        | 登录和购买独立开关                                         | ZEN 决定是否要求验证；Siteverify 的 success、action、hostname 校验及登录短期凭据仍保留 |
| 自邀返佣                         | 同一用户、联系邮箱或充值邮箱不返现                         | ZEN 判定；不拒绝购买本身                                                               |
| 首单返佣                         | 按用户、充值邮箱、联系邮箱检查历史成功订单                 | ZEN 判定；继续使用原事务锁和唯一约束                                                   |

业务频率额度统一放宽至原来的 2 倍，计数窗口保持不变；登录、验证码额度、未支付订单上限及提现审核条件保持不变。上游全局额度是本应用的调用预算，不能改变服务商自身的限流；上游错误状态和 `Retry-After` 仍按原流程处理。

原 `rate_limits` 表和旧 key 原样复用，包括旧邮箱 SHA-256 key，不清空或重建。多维度计数现在在一个事务中提交，所以一次被拒绝的请求也会消耗其适用的其他维度预算。请求必须同时满足各个适用维度的额度。

Better Auth 仍使用自己的协议限流器和 `auth_rate_limit` 表，应用配置的阈值由 ZEN 文档提供。SDK/plugin 内部的协议保护、OTP 尝试上限和会话校验继续保留；SDK 自身返回的限流结果目前不写入业务 `risk_events`。不会用业务风控替代身份验证、RBAC、最近登录要求、CSRF、支付验签、金额校验、资金与库存锁、幂等或订单状态机。

## 新增执行规则

所有规则现已切换为 `enforce`。频率超限返回 429，未支付订单达到上限时返回 403 并要求先处理已有订单；提现关联规则将申请交由人工审核。历史 `observe` 记录保留其当时的模式，不会被改写。

| 场景         | 关联与当前阈值                                              |
| ------------ | ----------------------------------------------------------- |
| 报价         | 同一可信 IP 或登录用户 60 次 / 分钟                         |
| 充值目标     | 同一充值邮箱 12 次 / 分钟；正式模式仅在上游已核对账号后计数 |
| 下单         | 同一可信 IP 或登录用户 40 次 / 10 分钟                      |
| 更新 Session | 同一可信 IP 或登录用户 40 次 / 分钟                         |
| 提现申请     | 同一可信 IP 或用户 10 次 / 10 分钟                          |
| 未支付订单   | 相同用户、联系邮箱或充值目标已经有至少 5 个未支付订单       |
| 共用收款账户 | 同一渠道、网络、收款账户关联至少 3 个不同用户               |
| 新账户提现   | 账号注册未满 24 小时                                        |

提现的 `review` 会进入现有 `pending` 人工审核流程并按原流程冻结申请金额；必须先受理，再登记实际打款，不能自动代付。返佣拒绝只拒绝佣金资格。风控“放行”仅表示允许该次业务操作，绝不授权访问其他人的订单。

上线后根据误伤与命中情况评估阈值，通过代码评审调整规则。下单拒绝会回滚本次事务的库存及报价绑定，保留独立的拒绝审计，不扣余额、不创建订单；原订单的幂等重试先返回已有结果，不因当前已达到上限而失败。

未支付订单数在所有上游预检与订单外键检查完成后、事务提交之前，以用户、联系邮箱、充值目标分别加事务锁复核，锁按固定顺序获取。计数排除本事务尚未提交的新订单，关联的并发创建串行完成“计数与提交”，避免多个请求同时越过五单上限；跨买家的风控锁不覆盖远程预检，保留库存 `SKIP LOCKED` 的并发行为。拒绝会回滚订单、库存及通知 outbox，再独立保存审计。取消或支付已有订单后，后续请求会读取新的未支付数量。充值目标只匹配套餐订单，钱包充值的账户邮箱不作为充值目标。

维度是否必填与执行模式分开配置：游客没有登录用户、未配置可信代理时没有可用 IP，这些可选维度跳过；浏览器授权标识、充值目标和提现用户等场景必需字段缺失则拒绝请求。不会为了启用 IP 规则而信任任意转发头。

## 关联、隐私与运维

- Cookie 仍用于游客订单授权和兼容旧计数。新增规则独立按用户、充值目标、邮箱、IP 等维度计数，不把多个维度拼成可被任意一个变化重置的单一 key。
- 仅当 `TRUST_PROXY=true` 时读取 `X-Real-IP`，要求入口代理覆盖该头并阻止绕过代理访问源站。不信任客户端提交的 `X-Forwarded-For` 或任意 Cloudflare 头；未配置可信代理时跳过 IP 维度，不把所有人归为 `127.0.0.1`。
- IP 校验并规范化；等价 IPv6 写法及 IPv4-mapped IPv6 不会产生不同 key。不采集 Canvas、字体等设备指纹。
- 新关联 key 使用现有加密密钥派生的、按用途隔离的 HMAC；日志不存邮箱、IP、收款账号明文、Session 或验证码 token。HMAC 属于去标识化，不等于匿名化。
- 收款账户按渠道和网络隔离。EVM 地址忽略大小写，TRON 地址保留大小写。其他收款账号保守地仅去除首尾空白；并不保证识别所有账号别名或实际控制人。
- `risk_events` 保存动作、实际处理、原因码、规则版本、指标、去标识关联 key 及订单／提现 ID。worker 每小时清理超过 30 天的记录；这是定期清理窗口，不是精确到秒的过期。
- 提现账户关联摘要随提现业务记录保留；旧计数到期后仍由 worker 清理。
- 新关联规则不会识别所有代理、多账号或共享账号情况。当前没有 IP 信誉库、支付付款人实名数据或设备身份证明。
- 引擎、计数或审计存储失败会使相关操作失败，不静默绕过安全检查。可通过后台、数据库及现有服务错误监控定位问题；不打印原始请求或引擎输入。

## 升级已有环境

使用已有数据库及原加密密钥，先备份，再在应用升级窗口执行：

```sh
bun install --frozen-lockfile
bun run db:migrate
bun run db:risk-backfill
bun run db:verify
bun run build
```

迁移新增 `risk_events` 表、提现关联摘要列与索引，不修改旧订单、余额、佣金和限流计数。回填命令使用原加密密钥解密历史提现账户并计算摘要，不输出账户明文，支持重复运行和失败后续跑。未回填的历史提现不参与账户关联统计，因此正式使用该统计前必须完成回填。之后重启 Web 和 worker。

原生 ZEN 包通过 Next.js `serverExternalPackages` 排除打包，生产环境需要安装对应平台的可选原生依赖；不要关闭 optional dependencies。规则 JSON 随应用打包，worker 和 Web 使用相同代码版本。
