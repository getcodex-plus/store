# 运维手册

## 更新与回滚

记录当前镜像摘要并备份数据库。用新镜像执行迁移和结构校验，再一起更新 Web、Worker，命令见[数据库维护](database.md)。不要用 `docker compose down -v` 更新，它会删除数据库卷。

回滚前确认旧版本能读取当前数据库、处理在途订单。已有按单采购订单时，不要回滚到不支持该模式的版本。

## 备份与恢复

- 每小时运行 [`backup-db.sh`](../scripts/ops/backup-db.sh)。用 `DB_CONTAINER` 指定 PostgreSQL 容器，`BACKUP_DIR` 指定备份目录，`REMOTE` 指定异地副本位置。保留 dump 及同批校验、行数文件。
- 将生效的加密密钥和认证密钥与数据库备份分开保管，不要在更新时重新生成。
- 每周运行 [`restore-drill.sh`](../scripts/ops/restore-drill.sh)。`DRILL_BASE_URL` 用 `__DB__` 代替库名；脚本在临时库验证结构、行数和凭据解密。`UNPROVEN` 表示没有可验证的库存凭据，不算解密通过。

## 订单巡检

上线首周由值班人每 30 分钟运行一次 [`sweep-stuck-orders.sh`](../scripts/ops/sweep-stuck-orders.sh)，指定实际数据库容器，保留 `RESULT:` 和待处理订单号。退出码 `0` 表示无需处理，`1` 表示有待处理订单，`2` 表示巡检未完成。

| 巡检结果 | 如何处理 |
| --- | --- |
| A 履约卡住 | 查 Worker 心跳、任务错误和上游订单。上游已扣款但未交付时，保留单号和流水，不要重新采购。 |
| B 疑似已付未入账 | 用订单号核对网关状态和实收金额。确认已付后通过渠道重发回调；买家截图、页面跳转都不是入账依据。 |
| C 支付建单失败 | 检查渠道连通性和回调地址，让买家从原订单重开收银台。 |
| D 退款超时 | 从受理时间起满 24 小时未打款即提醒；满 48 小时仍未打款，主动回复买家并记录原因。新人工退款为 `review`，巡检也覆盖旧的 `processing` 记录。 |

退款打款的内部目标是买家确认链与地址后 24 小时内。完成后登记币种、数量、链和交易哈希；巡检提醒本身不能证明款已退还。买家沟通见[客服处理](support-playbook.md)。
